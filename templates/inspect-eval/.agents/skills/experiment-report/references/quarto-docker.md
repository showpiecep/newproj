# Два Docker image для отчёта

## Разделение сборки

Предпочтительная структура:

```text
reports/
├── _quarto.yml
├── index.qmd
├── ab.qmd                 # если есть корректное A/B-сравнение
├── data/                  # производные таблицы, не редактируются вручную
└── _site/                 # готовая статика Quarto
tools/
├── build_report_data.py
└── build_report_snapshot.py
report-snapshot/           # полный снимок, не редактируется вручную
├── README.md              # состав и структура снимка
├── site/                  # готовый Quarto-сайт
├── raw/                   # .eval или допустимый полный экспорт
├── derived/               # таблицы расчётов и графиков
└── configs/               # очищенные run-конфиги
deploy/report/
└── Dockerfile
```

Исходники `.qmd`, `_quarto.yml` и Python-код подготовки данных версионируются.
`reports/data/`, `reports/_site/`, `report-snapshot/`, `reports/.quarto/` и
`*.quarto_ipynb` являются пересобираемыми артефактами и исключаются из Git.

Штатные команды проекта должны отражать стадии явно:

- `make report-data` полностью пересобирает таблицы из логов;
- `make report` зависит от `report-data` и рендерит `reports/_site`;
- `make report-preview` сначала обновляет данные, затем запускает локальный preview;
- `make report-snapshot` собирает сайт и снимок данных, очищенный от секретов;
- `make report-image` зависит от `report` и собирает лёгкий image;
- `make report-snapshot-image` зависит от `report-snapshot` и собирает полный image;
- `make report-image-serve` запускает лёгкий image на loopback-порту.

Если визуализация или Quarto переиспользует состояние ядра, отключить execute
daemon для воспроизводимого рендера. Preview должен выполнять начальный полный
рендер: изменение Parquet-файла может не считаться изменением `.qmd`.

## Лёгкий образ отчёта

Лёгкий image строится с build context `reports/_site` и обслуживает только готовую
статику через nginx:

```dockerfile
FROM nginx:alpine

ARG REPORT_VERSION=local
LABEL org.opencontainers.image.version="${REPORT_VERSION}"

COPY . /usr/share/nginx/html/

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
    CMD wget --quiet --output-document=/dev/null http://127.0.0.1/ || exit 1
```

Пример сборки и проверки:

```sh
docker build \
  --file deploy/report/Dockerfile \
  --build-arg REPORT_VERSION=local \
  --tag project-report:local \
  reports/_site

docker run --rm --publish 127.0.0.1:8770:80 project-report:local
```

Этот образ предназначен для удалённого сервера: в нём нет сырых данных, поэтому он
мал и дёшев в хранении и раздаче.

## Полный образ-снимок

Полный image строится отдельно из `report-snapshot/`, получает ту же версию и хранит
снимок, например в `/opt/report-snapshot`. Он включает сайт, исходные результаты,
производные таблицы, очищенные конфигурации и `README.md` с описанием структуры.

Данные не обязаны раздаваться по HTTP. Image является неизменяемым архивным
артефактом, а файлы при необходимости извлекаются стандартными средствами Docker.
Для образа-снимка достаточно минимального базового образа с возможностью создать
контейнер и скопировать из него каталог.

Назначение снимка — сохранить данные и контекст конкретного состояния эксперимента,
чтобы после долгого перерыва не искать прежние логи и промежуточные результаты, а
извлечь зафиксированный набор и сразу возобновить работу с ним.

Имена образов могут быть `project-report:<version>` и
`project-report-snapshot:<version>`. Версии должны совпадать, чтобы отчёт однозначно
связывался со своим снимком данных.

Публикацию в registry, CI/CD, SSH-деплой, внешний nginx и облачную инфраструктуру
добавлять только по отдельному запросу.

## Проверка

- Запустить лёгкий image и открыть главную страницу и все страницы навигации.
- Убедиться, что графики и интерактивные виджеты загрузились.
- Извлечь `/opt/report-snapshot` из полного image и проверить наличие ожидаемых
  логов, таблиц, конфигураций и описания структуры.
- Пересчитать ключевые агрегаты отчёта из извлечённых данных.
- Выборочно связать прогон, сэмпл, оценку и строку производной таблицы по их
  идентификаторам.
- Проверить, что полный image не содержит секретов и неочищенных credentials.
- Зафиксировать одну версию в labels обоих образов и показать её в отчёте.
