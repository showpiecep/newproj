# {{ project_name }}

Тестирующий сервис на [Inspect AI](https://inspect.aisi.org.uk/). Прогоняет набор
вопросов через тестируемый сервис, оценивает ответы LLM-судьёй по списку критериев
и складывает логи прогонов, пригодные для сравнения между собой.

HTTP-ручек у него нет — наружу он смотрит CLI-командами. Обычно такой репозиторий
живёт в паре с репозиторием самого сервиса.

## Быстрый старт

```bash
make init                                   # зависимости и git-хуки
make config                                 # config.yaml из шаблона
$EDITOR config.yaml                         # ключ судьи и адрес сервиса
make run RUN=configs/runs/service_eval.yaml # прогон
make view                                   # посмотреть логи
```

## Что уже собрано

Костяк рабочий: датасет-пример, критерии и промпт судьи лежат на своих местах, и
прогон запускается сразу. Дальше его расширяют, а не разбирают.

| Что | Где | Как расширять |
| --- | --- | --- |
| Вопросы к сервису | `data/questions.jsonl` | заменить своим набором; поля `id` и `question` обязательны, `reference` и `group` опциональны |
| Критерии оценки | `configs/runs/*.yaml` | добавить запись в `criteria`: имя становится ключом оценки и строкой в таблице метрик |
| Текст промпта судьи | `src/{{ project_slug }}/prompts/judge/v1/` | новая версия — новая папка `v2/`, версия выбирается в run-конфиге |
| Модель судьи | `configs/models/judge.yaml` | новый профиль — новый файл, ссылка по имени в run-конфиге |
| Тестируемый сервис | `src/{{ project_slug }}/infrastructure/http/` | другой протокол — новая реализация `ServiceUnderTest`, выбор в `evaluation/launch.py` |
| Новый вид прогона | `src/{{ project_slug }}/evaluation/` | своя поддиректория с `dataset.py`, `solver.py`, `task.py`; scorer и вьюер переиспользуются из `scoring/` |

## Структура

```text
configs/
  models/            профили моделей-судей, по файлу на профиль
  runs/              версионируемые описания прогонов
data/                датасеты; кода здесь нет
logs/                .eval-логи прогонов
src/{{ project_slug }}/
  main.py            точка входа: передаёт управление CLI
  evaluation/
    cli.py           команды прогона
    launch.py        конфигурация -> задача -> eval -> лог
    configuration/   строгие Pydantic-контракты YAML прогона и профиля судьи
    service_eval/    задача: спросить сервис, оценить ответ судьёй
    scoring/         scorer, сборка значения score, настройка вьюера
  prompts/           версионируемые Jinja-шаблоны промптов
  application/       порт тестируемого сервиса
  domain/            вердикт судьи и его разбор; не знает про Inspect AI
  infrastructure/    реализации порта
  settings/          мастер-конфиг: ключи и адреса
    config.py        единственный публичный модуль пакета
    sections/        разделы конфигурации, по файлу на раздел
    artifacts/       генерация config.template.yaml и config.schema.json
tests/
```

Поток запуска: `configs/runs/*.yaml` → `launch` → сборка `Task` → `inspect_ai.eval` →
`.eval`-лог. Домен не зависит ни от YAML, ни от Click, ни от HTTP-клиента, ни от
конкретной LLM.

## Разделение конфигураций

- `config.yaml` — секреты и локальные адреса. Не в репозитории, у каждого свой.
  Собирается из `config.template.yaml`; рядом лежит `config.schema.json`, по которой
  редактор (расширение YAML) подсвечивает и дополняет конфиг. Оба файла пересобирает
  pre-commit-хук `config-artifacts` и `make config-template`.
- `configs/runs/*.yaml` — параметры прогона: датасет, критерии, судья, версия
  промпта. Версионируются, потому что без них результат нельзя воспроизвести.

## Незаполненный конфиг

Поле, без которого приложение работать не будет, помечено в моделях настроек
`must_be_filled`. Пустое значение и плейсхолдер `<имя_поля>` из шаблона проходят
валидацию типов, поэтому такие поля проверяются отдельно — при загрузке
конфигурации, все разом, до обращения к внешним системам:

```text
config.yaml заполнен не полностью:
  judge.api_key — ключ провайдера модели-судьи; без него прогон не сможет
                  обратиться к судье
      сейчас: незаполненный плейсхолдер "<api_key>"
Заполните эти поля и повторите запуск.
```

Запуск прекращается с кодом 1 и без traceback: это сообщение оператору, а не сбой
программы. Иначе прогон стартовал бы и упал позже отказом провайдера, потратив
время и токены.

## Работа с логами

```bash
make view                       # просмотр прогонов
make score LOG=logs/<файл>.eval # переоценить лог, не гоняя сервис заново
```

Переоценка готового лога — штатный путь при правке рубрики судьи: тестируемый
сервис при этом не вызывается, платите только за судью. Тем же способом сравнивают
несколько судей на одних и тех же данных.

Для анализа результатов брать `evals_df()` / `samples_df()` из
`inspect_ai.analysis`, а не разбирать `.eval` самостоятельно.

Отчёты по накаткам предпочтительно собирать как сайт Quarto. Рекомендуемый поток:
`.eval`-логи → проверяемый Python-сборщик → Parquet → `.qmd`-страницы. Сборщик начинает
со всех логов, явно сообщает об исключённых и сравнивает прогоны только внутри групп с
одинаковыми условиями измерения. Подробные правила описаны в `AGENTS.md`.

## Коммиты, PR и issue

Сообщения коммитов — в формате [Conventional Commits](https://www.conventionalcommits.org/ru/):
`feat(scope): …`, `fix: …`, `refactor: …`. Хук `commit-msg` только подсказывает
формат и коммит не блокирует: срочный коммит важнее идеального сообщения, поправить
его можно через `git commit --amend`.

Второй хук считает файлы одного расширения в директориях, которых коснулся
коммит, и предупреждает, если их больше пяти: обычно это значит, что часть
файлов об одном и просится в поддиректорию со своим именем. Порог — эвристика,
а не правило, поэтому хук тоже не блокирует коммит; изменить порог можно в
`.pre-commit-config.yaml` (`--max`).

В `.github/` лежат шаблон описания PR, формы для issue (ошибка, задача) и два
workflow. GitHub подхватывает их автоматически.

## CI и релизы

`ci.yml` ставит зависимости (`uv sync --locked --all-groups`) и прогоняет
`make check` на каждый PR и push в `main` — линтер, проверку форматирования,
сверку шаблона конфигурации и тесты. Хуки pre-commit ставятся локально и не у
всех, поэтому в CI дублируется всё, что они делают: это единственная проверка,
через которую пройдут все. `make init` в CI не вызывается намеренно:
он пересобрал бы `config.template.yaml` и `config.schema.json`, и сверка перестала
бы что-либо проверять. Поэтому первый push должен идти уже после локального
`make init`, иначе в репозитории не будет `config.schema.json`.

`release.yml` срабатывает на тег `v*` и публикует релиз на GitHub. Состояние кода
фиксируется осознанно, поэтому workflow требует аннотированный тег и берёт его
текст как описание релиза. Отчёты об экспериментах ссылаются на релиз,
поэтому в аннотации стоит написать, каким прогонам соответствует это состояние
стенда:

```bash
# version в pyproject.toml должен совпадать с тегом без v
git tag -a v0.2.0 \
  -m "Стенд с новой рубрикой судьи" \
  -m "Изменилась формула оценки: с прежними прогонами метрики несравнимы."
git push origin v0.2.0
```

Первая строка становится началом описания релиза, остальные — пояснением, ниже
GitHub дописывает список изменений. Тег без аннотации, пустая аннотация и
расхождение тега с `version` в `pyproject.toml` останавливают workflow с
подсказкой, что поправить. Если тег перевесить и запустить заново, описание
релиза обновится.
