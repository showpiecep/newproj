# {{ project_name }}

Тестирующий сервис на [Inspect AI](https://inspect.aisi.org.uk/): прогоняет набор
вопросов через тестируемый сервис, оценивает ответы LLM-судьёй по списку критериев
и складывает логи прогонов, пригодные для сравнения между собой.

HTTP-ручек у него нет — наружу он смотрит CLI-командами. Обычно такой репозиторий
живёт в паре с репозиторием самого сервиса.

## Быстрый старт

```bash
make init                                   # зависимости и git-хуки
make config                                 # config.yaml из шаблона
$EDITOR config.yaml                         # ключ судьи и адрес сервиса
make run RUN=configs/runs/service_eval.yaml # прогон
make view                                   # посмотреть логи
```

## Что уже собрано

Костяк рабочий: датасет-пример, критерии и промпт судьи лежат на своих местах, и
прогон запускается сразу. Дальше его расширяют, а не разбирают.

| Что | Где | Как расширять |
| --- | --- | --- |
| Вопросы к сервису | `data/questions.jsonl` | заменить своим набором; поля `id` и `question` обязательны, `reference` и `group` опциональны |
| Критерии оценки | `configs/runs/*.yaml` | добавить запись в `criteria`: имя становится ключом оценки и строкой в таблице метрик |
| Текст промпта судьи | `src/{{ project_slug }}/prompts/judge/v1/` | новая версия — новая папка `v2/`, версия выбирается в run-конфиге |
| Модель судьи | `configs/models/judge.yaml` | новый профиль — новый файл, ссылка по имени в run-конфиге |
| Тестируемый сервис | `src/{{ project_slug }}/infrastructure/http/` | другой протокол — новая реализация `ServiceUnderTest`, выбор в `evaluation/launch.py` |
| Новый вид прогона | `src/{{ project_slug }}/evaluation/` | своя поддиректория с `dataset.py`, `solver.py`, `task.py`; scorer и вьюер переиспользуются из `scoring/` |

## Структура

```text
configs/
  models/            профили моделей-судей, по файлу на профиль
  runs/              версионируемые описания прогонов
data/                датасеты; кода здесь нет
logs/                .eval-логи прогонов
src/{{ project_slug }}/
  main.py            точка входа: передаёт управление CLI
  evaluation/
    cli.py           команды прогона
    launch.py        конфигурация -> задача -> eval -> лог
    configuration/   строгие Pydantic-контракты YAML прогона и профиля судьи
    service_eval/    задача: спросить сервис, оценить ответ судьёй
    scoring/         scorer, сборка значения score, настройка вьюера
  prompts/           версионируемые Jinja-шаблоны промптов
  application/       порт тестируемого сервиса
  domain/            вердикт судьи и его разбор; не знает про Inspect AI
  infrastructure/    реализации порта
  settings/          мастер-конфиг: ключи и адреса
tests/
```

Поток запуска: `configs/runs/*.yaml` → `launch` → сборка `Task` → `inspect_ai.eval` →
`.eval`-лог. Домен не зависит ни от YAML, ни от Click, ни от HTTP-клиента, ни от
конкретной LLM.

## Разделение конфигураций

- `config.yaml` — секреты и локальные адреса. Не в репозитории, у каждого свой.
- `configs/runs/*.yaml` — параметры прогона: датасет, критерии, судья, версия
  промпта. Версионируются, потому что без них результат нельзя воспроизвести.

## Работа с логами

```bash
make view                       # просмотр прогонов
make score LOG=logs/<файл>.eval # переоценить лог, не гоняя сервис заново
```

Переоценка готового лога — штатный путь при правке рубрики судьи: тестируемый
сервис при этом не вызывается, платите только за судью. Тем же способом сравнивают
несколько судей на одних и тех же данных.

Для анализа результатов брать `evals_df()` / `samples_df()` из
`inspect_ai.analysis`, а не разбирать `.eval` самостоятельно.

## Правила разработки

[AGENTS.md](AGENTS.md) — в том числе то, как устроены метрики: почему значение score
словарь, почему число метрик не должно расти вместе с датасетом и что ломается при
