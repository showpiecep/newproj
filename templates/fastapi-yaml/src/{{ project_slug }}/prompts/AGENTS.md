# Промпты

## Промпты и KV-cache

- При работе с LLM проектировать промпты с учётом высокого KV-cache hit rate, чтобы
  уменьшать задержку и стоимость запросов.
- Общие системные инструкции, схемы инструментов и другой неизменяемый контекст
  размещать в стабильном префиксе промпта.
- Динамические данные пользователя, результаты поиска, временные метки, идентификаторы
  запросов и другой изменяемый контекст размещать после стабильного префикса.
- Не менять без необходимости формулировки, порядок блоков, пробелы и сериализацию
  общего префикса между однотипными запросами.
- Использовать детерминированную сериализацию структурированных данных: сохранять
  порядок полей и избегать случайного переупорядочивания элементов.
- Переиспользовать общие версии промптов вместо создания почти одинаковых вариантов
  для каждого сценария. Изменяемые части передавать отдельными последующими блоками.
- Оценивать изменения промптов по фактическому cache hit rate, стоимости, задержке и
  качеству ответов.
- Оптимизация KV-cache не должна ухудшать корректность, безопасность или полноту
  необходимого контекста.

## Организация промптов и структурированные ответы

- Все промпты хранить отдельно от Python-кода в этом пакете; не размещать
  многострочные промпты непосредственно в исходном коде.
- Каждый промпт хранить в отдельном шаблоне Jinja с расширением `.jinja`.
  Организовывать шаблоны по тематическим директориям и назначению, например
  `prompts/<область>/<сценарий>/system.jinja` и `user.jinja`.
- Динамические значения передавать в промпты через явно названные переменные Jinja.
  Не переносить в шаблоны бизнес-логику и сложные вычисления.
- Считать файлы промптов самостоятельными версионируемыми артефактами. Изменения
  текста промпта должны быть видны в истории версий отдельно от изменений кода,
  который выполняет запрос к модели.
- Если модель должна вернуть JSON, по умолчанию не использовать Structured Outputs,
  JSON Schema response format и другие механизмы принудительного структурирования
  ответа на уровне API. Они могут ухудшать качество ответа и поддерживаются не всеми
  моделями и провайдерами.
- Требуемую структуру JSON явно описывать в инструкции промпта: перечислять поля,
  допустимые значения и требовать вернуть только JSON без Markdown и текста вокруг.
- Ответ модели сначала разбирать стандартным `json.loads`. Если JSON синтаксически
  повреждён, использовать `json_repair.repair_json` как fallback, после чего
  обязательно валидировать полученный объект через Pydantic-модель или эквивалентную
  явную проверку контракта.
- Не считать успешное исправление через `json_repair` подтверждением смысловой
  корректности ответа. Ошибки обязательных полей, типов и допустимых значений должны
  обрабатываться явно.
- Structured Outputs допустимы только как обоснованное исключение, если конкретная
  модель и провайдер их поддерживают, а измерения на целевом наборе данных
  подтверждают, что принудительная схема не ухудшает качество.
- Для промптов проверять как минимум успешный рендер Jinja с тестовыми данными и
  соответствие разобранного ответа ожидаемому контракту.
