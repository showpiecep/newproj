# {{ project_name }}

FastAPI-шаблон с типизированной конфигурацией из YAML. `.env` не используется:
вложенность остаётся обычной YAML-вложенностью, а вся структура проверяется
Pydantic при старте приложения.

## Быстрый старт

```bash
git init
make init
make config
# Впишите в config.yaml секреты и обязательные поля, если они есть
make run
```

`make init` устанавливает зависимости и включает pre-commit-хуки. Если каталог
ещё не является git-репозиторием, установка хуков пропускается с подсказкой:
выполните `git init`, затем `make hooks`.

После запуска доступны API на <http://127.0.0.1:{{ service_port }}> и документация
на <http://127.0.0.1:{{ service_port }}/docs>.

## Как устроена конфигурация

`config.template.yaml` коммитится и описывает полное дерево настроек.
`config.yaml` создаётся локально, содержит реальные секреты и игнорируется Git.

`make config` создаёт минимальный `config.yaml`: только секреты и обязательные
поля, остальное приложение берёт из умолчаний моделей. Поэтому в файле видно
только то, что задано осознанно, а новые умолчания подхватываются без его правки.
Нужное поле дописывается по шаблону или автодополнению схемы; полная копия
шаблона — `cp config.template.yaml config.yaml`. Существующий `config.yaml`
команда не перезаписывает.
Путь к другому YAML можно передать приложению программно:

```python
config = Config.load(Path("/run/secrets/service-config.yaml"))
app = Application(config).create_app()
```

Такой явный путь удобен для Docker/Kubernetes: YAML монтируется как один secret
volume без преобразования вложенных ключей в переменные окружения.

`Config` — мастер-модель, содержащая вложенные секции настроек. Каждая новая область
конфигурации получает отдельный модуль в пакете `settings`, после чего добавляется
полем в `Config`.

При каждом запуске bootstrap строит актуальный `config.template.yaml`
непосредственно из Pydantic-моделей до чтения пользовательского конфига. Благодаря
этому структура шаблона не расходится со структурой кода даже тогда, когда старый
`config.yaml` уже не проходит валидацию. После загрузки конфига bootstrap также
учитывает путь из поля `app.config_template_path`.

Рядом с шаблоном пишется `config.schema.json` — JSON Schema конфига из тех же
моделей. С расширением [YAML](https://marketplace.visualstudio.com/items?itemName=redhat.vscode-yaml)
редактор подсвечивает опечатки в ключах и недопустимые значения и дополняет поля:
шаблон и созданный `make config` `config.yaml` ссылаются на схему первой строкой
`# yaml-language-server: $schema=./config.schema.json`, а для конфигов без этой
строки схема привязана через `.vscode/settings.json`.

Оба файла пересобирает pre-commit-хук `config-artifacts` (вручную —
`make config-template`): если они отстали от моделей, коммит остановится с уже
обновлёнными файлами, их нужно добавить в коммит. `make config-check` только
сверяет без записи.

При запуске через `make run` Uvicorn получает `host` и `port` из `config.yaml`.

## Незаполненный конфиг

Поле, без корректного значения которого приложение работать не будет
(ключ, адрес внешней системы), объявляется через `must_be_filled` из
`settings/requirements/`:

```python
api_key: SecretStr = must_be_filled(
    SecretStr(""),
    "ключ платёжного провайдера; без него оплата работать не будет",
)
```

Пустое значение и плейсхолдер `<имя_поля>` из шаблона проходят валидацию типов,
поэтому такие поля проверяются отдельно — при загрузке конфигурации, все разом,
до обращения к внешним системам. Сервис не стартует, печатает какое поле,
зачем оно и что сейчас стоит вместо значения, и выходит с кодом 1 без traceback.
В этом шаблоне таких полей пока нет: их добавляют вместе с первой внешней
зависимостью.

## Логирование

Прикладной код использует Loguru напрямую:

```python
from loguru import logger

logger.info("Application event")
```

Уровень и JSON-сериализация задаются секцией `logging` в `config.yaml`.
Логи Uvicorn, FastAPI и сторонних библиотек не перехватываются и продолжают
работать через собственные механизмы.

## Состояние приложения

`app.state` представлен типизированным `ApplicationState`. Когда в lifespan
появляется новый общий ресурс, его поле добавляется в `application/state.py`.
После этого обращения к состоянию получают автодополнение и статическую проверку
типов вместо неявных динамических атрибутов.

Исходный пакет намеренно остаётся минимальным:

```text
src/{{ project_slug }}/
├── main.py
├── application/
│   ├── app.py
│   ├── bootstrap.py
│   ├── state.py
│   └── routers/
│       └── __init__.py
├── settings/
│   ├── config.py          мастер-конфиг: единственный публичный модуль пакета
│   ├── sections/          разделы конфигурации, по файлу на раздел
│   │   ├── app.py
│   │   ├── base.py
│   │   └── logging.py
│   └── artifacts/         генерация config.template.yaml, config.schema.json
│       ├── minimal.py     и минимального config.yaml

│       └── template.py
├── observability/

└── usecases/
    └── __init__.py
```

## Docker

```bash
docker build -t {{ project_slug }}:local .
docker run --rm -p {{ service_port }}:{{ service_port }} \
    -v ./config.yaml:/app/config.yaml:ro {{ project_slug }}:local
```

Образ собирается в две стадии. Стадия `builder` одинакова для любого проекта на
uv: ставит зависимости из `uv.lock` отдельным слоем, а прикладной код — следующим,
поэтому правка кода не переустанавливает зависимости. Стадия рантайма —
место для настроек конкретного проекта: порт, `HEALTHCHECK`, системные пакеты.
Секретов в образе нет: `config.yaml` монтируется при запуске, а в контекст сборки
попадают только файлы из `.dockerignore`. Для сборки нужен `uv.lock` — его создаёт
`make init`.

## Проверки

```bash
make test
make lint          # ruff check
make format-check  # ruff format --check
make format        # переформатировать на месте
make check         # всё вышеперечисленное, кроме format
```

`make check` — ровно то, что гоняет CI. Форматирование проверяется отдельной
командой, потому что локально его молча делает pre-commit, а без установленных
хуков этого не происходит и заметить должен CI.

## Коммиты, PR и issue

Сообщения коммитов — в формате [Conventional Commits](https://www.conventionalcommits.org/ru/):
`feat(scope): …`, `fix: …`, `refactor: …`. Хук `commit-msg` только подсказывает
формат и коммит не блокирует: срочный коммит важнее идеального сообщения, поправить
его можно через `git commit --amend`.

Второй хук считает файлы одного расширения в директориях, которых коснулся
коммит, и предупреждает, если их больше пяти: обычно это значит, что часть
файлов об одном и просится в поддиректорию со своим именем. Порог — эвристика,
а не правило, поэтому хук тоже не блокирует коммит; изменить порог можно в
`.pre-commit-config.yaml` (`--max`).

В `.github/` лежат шаблон описания PR, формы для issue (ошибка, задача) и два
workflow. GitHub подхватывает их автоматически.

## CI и релизы

`ci.yml` ставит зависимости (`uv sync --locked --all-groups`) и прогоняет
`make check` на каждый PR и push в `main` — линтер, проверку форматирования,
сверку шаблона конфигурации и тесты. Хуки pre-commit ставятся локально и не у
всех, поэтому в CI дублируется всё, что они делают: это единственная проверка,
через которую пройдут все. `make init` в CI не вызывается намеренно:
он пересобрал бы `config.template.yaml` и `config.schema.json`, и сверка перестала
бы что-либо проверять. Поэтому первый push должен идти уже после локального
`make init`, иначе в репозитории не будет `config.schema.json`.

`release.yml` срабатывает на тег `v*` и публикует релиз на GitHub. Состояние кода
фиксируется осознанно, поэтому workflow требует аннотированный тег и берёт его
текст как описание релиза:

```bash
# version в pyproject.toml должен совпадать с тегом без v
git tag -a v0.2.0 \
  -m "Поддержка пакетной обработки" \
  -m "С этого состояния разворачивается production, контракт эндпоинта зафиксирован."
git push origin v0.2.0
```

Первая строка становится началом описания релиза, остальные — пояснением, ниже
GitHub дописывает список изменений. Тег без аннотации, пустая аннотация и
расхождение тега с `version` в `pyproject.toml` останавливают workflow с
подсказкой, что поправить. Если тег перевесить и запустить заново, описание
релиза обновится.
