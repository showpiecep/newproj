# Правила репозитория

Репозиторий содержит Copier-шаблоны проектов и установщик команды `newproj`.
Правила разработки конкретного проекта живут внутри своего шаблона, например
[templates/fastapi-yaml/AGENTS.md](templates/fastapi-yaml/AGENTS.md), и
относятся к сгенерированному проекту, а не к этому репозиторию.

## Границы

- В `templates/<имя>/` лежит только содержимое будущего проекта. Ни установщик,
  ни CI, ни документация репозитория туда не попадают.
- В корне лежит только инфраструктура распространения: `install.sh`,
  `installer/`, `.github/`, документация репозитория.
- Файлы шаблона рендерятся Jinja (`_templates_suffix: ""`), поэтому любой
  `{{` или `{%` внутри шаблона обязан быть осознанным. Файлы репозитория
  Jinja не обрабатываются.
- Если файл шаблона обязан попасть в проект с Jinja будущего проекта внутри
  (шаблоны промптов, конфиги другого шаблонизатора), его содержимое нужно
  обернуть в `{% raw %}` … `{% endraw %}`. Ключа `_copy_without_render` в
  Copier 9 нет: он молча игнорируется, и Copier вычистит из такого файла все
  плейсхолдеры, оставив пустые строки вместо переменных.

## Шаблоны

- Один каталог в `templates/` — один шаблон с собственным `copier.yml`.
- Новый шаблон не требует правок установщика или `newproj.zsh`: оба находят
  шаблоны по наличию `copier.yml`.
- Артефакты локальной работы (`config.yaml`, `.venv`, кеши) должны быть в
  `_exclude`, иначе они попадут в сгенерированный проект при генерации из
  рабочей копии.

## Скрипты

- `install.sh`, `uninstall.sh` и `installer/build-release.sh` — переносимый
  POSIX `sh`, без расширений bash и zsh.
- `install.sh` и `uninstall.sh` загружаются по сети и выполняются напрямую,
  поэтому обязаны оставаться самодостаточными: общие помощники в них повторены
  осознанно, выносить их в отдельный файл нельзя.
- Разбор маркеров rc-файла обязан совпадать в обоих скриптах: установщик и
  деинсталлятор работают с одним и тем же блоком.
- `installer/newproj.zsh` — Zsh; функция обязана работать при `zsh -df`.
- Установщик изменяет файлы пользователя, поэтому обязателен порядок
  «сначала все проверки, затем изменения»: любая правка должна сохранять
  проверку контрольной суммы, `zsh -n` перед записью rc-файла, резервную копию
  rc-файла, отказ трогать неуправляемый шаблон и откат при неудачной подмене.
- Управляемый блок в rc-файле ограничен маркерами `# >>> newproj >>>` и
  `# <<< newproj <<<`; повторная установка обязана оставаться идемпотентной.
- Обновление — это повторный запуск установщика, поэтому идемпотентность
  проверяется побайтово: rc-файл переписывается и резервируется только когда
  управляемый блок изменился, а хвостовые пустые строки нормализуются.
- `install.sh` кладёт в каталог установки свою копию и файл `state`; `newproj
  update` запускает эту копию с настройками оттуда. Подмена файлов в каталоге
  установки обязана оставаться через `mv`: установщик заменяет сам себя, и
  переименование не задевает inode, который читает запущенный `sh`.
- Версия установки берётся из имени корневого каталога архива
  (`newproj-templates-<версия>`), а не из `NEWPROJ_VERSION`: по умолчанию там
  стоит `latest`. Менять префикс в `build-release.sh` нельзя, не поправив разбор
  в установщике.
- Проверка обновлений в оболочке обязана быть неблокирующей и молчащей при
  ошибке: запрос уходит в отсоединённый фон, баннер печатается из кеша, а
  `NEWPROJ_UPDATE_CHECK_DAYS=0` выключает и проверку, и баннер.

## Сайт и changelog

- `docs/` — сайт репозитория на Quarto, публикуется на GitHub Pages workflow'ом
  `.github/workflows/docs.yml` при push в `main` и после успешной публикации
  релиза. Триггер по тегу ставить нельзя: окружение `github-pages` разрешает
  деплой только с `main` и отклоняет запуск на ref тега.
- Changelog собирается `git-cliff` из истории коммитов при каждой сборке; файла
  в репозитории нет и заводить его не нужно. Поэтому сообщения коммитов —
  пользовательский текст: conventional commits обязательны, тип определяет
  раздел, область в скобках — префикс строки.
- `docs/_changelog.md` генерируется и лежит в `.gitignore`. Локальный рендер без
  него падает: сначала `git-cliff`, потом `quarto`.
- Сайт и `README.md` описывают одно и то же поведение с разной подробностью.
  Изменение поведения установщика правит оба; расхождение между ними —
  ошибка, а не вопрос вкуса.
- `docs/`, `cliff.toml` и `.github/` исключены из релизного архива через
  `.gitattributes`: `git archive` не должен класть их на машины пользователей.

## Проверка изменений

- После правок установщика запускать `sh installer/test-install.sh` — тест
  работает в изолированном `HOME` и не трогает файлы пользователя.
- После правок шаблона проверять генерацию и быстрые проверки полученного
  проекта: `copier copy templates/<имя> <путь> --trust` и `make check`.
