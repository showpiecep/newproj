# Правила разработки

## Общие принципы

- Соблюдать SRP, SOLID, DRY и KISS.
- Не добавлять код, абстракции, зависимости и инфраструктурные компоненты, пока в них
  нет реальной потребности.
- Каждый класс, модуль и пакет должен иметь одну понятную ответственность.
- Предпочитать простой явно написанный код преждевременной универсальности.
- Не дублировать бизнес-правила и знания о предметной области.

## Архитектура

- По возможности придерживаться луковой архитектуры.
- Бизнес-логика и модели предметной области не должны зависеть от FastAPI, баз
  данных, внешних API, конкретных моделей машинного обучения и других деталей
  инфраструктуры.
- Зависимости должны быть направлены от внешних слоёв к внутренним.
- Внешние реализации подключаются к приложению в точке сборки приложения.
- Не создавать фиктивные реализации и заготовки для сервисов, которые ещё не нужны
  проекту.

## Интерфейсы и реализации

- Интерфейсы объявлять только через `abc.ABC` и `abc.abstractmethod`.
- Использование `typing.Protocol` запрещено.
- Код, использующий компонент, должен зависеть от его интерфейса, а не от конкретной
  реализации.
- Если появляются несколько взаимозаменяемых реализаций одного компонента, для них
  необходимо выделить общий интерфейс.
- Например, разные модели эмбеддингов с разным способом инференса должны находиться
  в отдельном пакете работы с моделями, реализовывать единый ABC-интерфейс и
  использоваться остальным приложением только через этот интерфейс.

## Структура файлов и директорий

- SRP применяется не только к классам, но также к файлам и директориям.
- Одна директория должна объединять только компоненты одной предметной или
  технической области.
- Один файл должен решать одну задачу; несвязанные классы и функции нельзя складывать
  вместе ради уменьшения количества файлов.
- На верхнем уровне исходного Python-пакета должна находиться только точка входа
  приложения. Вспомогательные модули необходимо размещать в тематических
  поддиректориях.
- Конкретные реализации, интерфейсы, конфигурация и логика сборки приложения должны
  быть разделены, если у них разные причины для изменения.
- Новую тематическую директорию следует создавать при появлении самостоятельной
  области ответственности, а не заранее.

## Промпты и KV-cache

- При работе с LLM проектировать промпты с учётом высокого KV-cache hit rate, чтобы
  уменьшать задержку и стоимость запросов.
- Общие системные инструкции, схемы инструментов и другой неизменяемый контекст
  размещать в стабильном префиксе промпта.
- Динамические данные пользователя, результаты поиска, временные метки, идентификаторы
  запросов и другой изменяемый контекст размещать после стабильного префикса.
- Не менять без необходимости формулировки, порядок блоков, пробелы и сериализацию
  общего префикса между однотипными запросами.
- Использовать детерминированную сериализацию структурированных данных: сохранять
  порядок полей и избегать случайного переупорядочивания элементов.
- Переиспользовать общие версии промптов вместо создания почти одинаковых вариантов
  для каждого сценария. Изменяемые части передавать отдельными последующими блоками.
- Оценивать изменения промптов по фактическому cache hit rate, стоимости, задержке и
  качеству ответов.
- Оптимизация KV-cache не должна ухудшать корректность, безопасность или полноту
  необходимого контекста.

## Оценивание и тестирующие системы

- Если проект содержит функциональность для оценки качества модели, агента или
  внешнего сервиса через API, выполняет прогоны на наборах данных, сравнивает
  варианты или анализирует результаты экспериментов, по умолчанию использовать
  [Inspect AI](https://inspect.aisi.org.uk/).
- Считать Inspect AI базовой лучшей практикой для оценочной инфраструктуры: сначала
  использовать и расширять его готовые абстракции, а не создавать собственный
  фреймворк прогонов.
- Представлять оценивание через стандартные сущности Inspect AI: `Task`, `Dataset`,
  `Solver`, `Scorer` и метрики. Специфичную логику интегрировать через предусмотренные
  точки расширения.
- Для проверяемого API или нестандартного сервиса реализовывать адаптер в подходящем
  расширяемом компоненте Inspect AI, сохраняя стандартный жизненный цикл прогона,
  сбор результатов и формат логов.
- Использовать версии задач, метаданные, теги и конфигурацию прогонов для
  воспроизводимости и сравнения результатов.
- Сохранять eval-логи Inspect AI и использовать `inspect view` или Inspect View для
  просмотра прогонов, отдельных примеров, ответов, оценок и ошибок.
- Перед созданием собственной системы запуска, логирования, версионирования,
  агрегации метрик или пользовательского интерфейса проверить, решается ли задача
  штатными средствами или расширениями Inspect AI.
- Отказ от Inspect AI для оценочной подсистемы должен быть явно обоснован конкретным
  техническим ограничением фреймворка.
- Inspect AI не заменяет обычные модульные и интеграционные тесты с детерминированным
  ожидаемым результатом; для них продолжать использовать стандартный тестовый
  фреймворк проекта.

## Изменение проекта

- Сначала использовать существующие точки расширения и только затем добавлять новые.
- Не удалять и не переписывать существующий код без явной необходимости в рамках
  поставленной задачи.
- Любая новая абстракция должна быть оправдана существующими реализациями или
  подтверждённым требованием.
- Рефакторинг должен сохранять внешнее поведение, если его изменение не запрошено
  отдельно.
